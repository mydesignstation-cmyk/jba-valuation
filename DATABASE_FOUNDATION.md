# Neon Database Foundation

This document outlines the database foundation created for the VA2 project using Neon PostgreSQL and Drizzle ORM.

## Overview

A complete Neon database foundation has been established to support the following validated entities:

- **Customers**
- **Banks**
- **Branches** (independent master entity)
- **Cases** (business transactions with relationships to customers, banks, and branches)

## Database Schema

### Customers Table
- `id` (UUID): Primary key
- `name` (VARCHAR): Customer name (required)
- `contact` (VARCHAR): Contact information (required)
- `email` (VARCHAR): Email address (optional)
- `address` (TEXT): Physical address (required)
- `created_at` (TIMESTAMP): Auto-set creation timestamp
- `updated_at` (TIMESTAMP): Auto-set update timestamp

**Indexes:**
- `customers_email_idx` on email
- `customers_created_at_idx` on created_at

### Banks Table
- `id` (UUID): Primary key
- `name` (VARCHAR): Bank name (required)
- `created_at` (TIMESTAMP): Auto-set creation timestamp
- `updated_at` (TIMESTAMP): Auto-set update timestamp

**Indexes:**
- `banks_created_at_idx` on created_at

### Branches Table
- `id` (UUID): Primary key
- `name` (VARCHAR): Branch name (required)
- `created_at` (TIMESTAMP): Auto-set creation timestamp
- `updated_at` (TIMESTAMP): Auto-set update timestamp

**Note:** Branch is an independent master entity with no foreign key to banks.

**Indexes:**
- `branches_created_at_idx` on created_at

### Cases Table
- `id` (UUID): Primary key
- `case_number` (VARCHAR): Unique case identifier
- `request_number` (VARCHAR): External request reference
- `customer_id` (UUID): Foreign key to customers (RESTRICT on delete)
- `bank_id` (UUID): Foreign key to banks (RESTRICT on delete)
- `branch_id` (UUID): Foreign key to branches (RESTRICT on delete)
- `assigned_engineer_id` (UUID): Reference to assigned site engineer (nullable)
- `stage` (VARCHAR): Case workflow stage (default: 'CREATED')
- `created_by_id` (UUID): Reference to creator user (nullable)
- `created_at` (TIMESTAMP): Auto-set creation timestamp
- `updated_at` (TIMESTAMP): Auto-set update timestamp

**Indexes:**
- `cases_case_number_idx` on case_number
- `cases_request_number_idx` on request_number
- `cases_customer_id_idx` on customer_id
- `cases_bank_id_idx` on bank_id
- `cases_branch_id_idx` on branch_id
- `cases_assigned_engineer_id_idx` on assigned_engineer_id
- `cases_stage_idx` on stage
- `cases_created_at_idx` on created_at

## Database Files

### Configuration
- `drizzle.config.ts` - Drizzle ORM configuration pointing to Neon PostgreSQL

### Schema Definition
- `src/db/schema.ts` - Complete Drizzle schema with table definitions, foreign keys, indexes, and relations

### Database Client
- `src/db/index.ts` - Database initialization and Drizzle instance export

### Migrations
- `src/db/migrations/` - Migration files generated by Drizzle Kit
  - `0000_petite_dragon_lord.sql` - Initial migration creating all tables and indexes
  - `meta/` - Migration metadata

### Migration Runner
- `src/db/migrate.ts` - Script to run migrations against Neon database

## Foreign Keys and Constraints

All foreign keys use `ON DELETE RESTRICT` to prevent accidental deletion of referenced entities:

- Cases → Customers: Cannot delete a customer with related cases
- Cases → Banks: Cannot delete a bank with related cases
- Cases → Branches: Cannot delete a branch with related cases

## Relationships

- **Customers** have many Cases
- **Banks** have many Cases
- **Branches** have many Cases
- **Cases** reference one Customer, one Bank, and one Branch

## Environment Setup

The database connection uses the following environment variables (from `.env.local`):

- `DATABASE_URL` - Pooled connection string (for applications)
- `DATABASE_URL_UNPOOLED` - Unpooled connection string (for migrations and CLI tools)

## Running Migrations

To apply migrations to the database:

```bash
npm run db:migrate
# or
npx tsx src/db/migrate.ts
```

## Notes

1. **No User/Auth Foreign Keys**: Site Engineers are currently mock users, so no foreign key to a real user/auth table exists yet. The `assigned_engineer_id` and `created_by_id` fields are nullable UUIDs for future integration.

2. **UI and Services Unchanged**: This database foundation is isolated in `src/db/`. The existing mock services and UI components remain unchanged and fully functional.

3. **Incremental Integration**: The mock services are ready to be gradually replaced with database-backed services without affecting the UI layer.

4. **Case Number Generation**: Cases have both `case_number` (system-generated, unique, format: VAL-YYYY-NNNN) and `request_number` (external reference).
